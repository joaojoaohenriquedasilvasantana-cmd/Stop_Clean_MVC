Autenticação Separada por Perfil

Cliente e funcionário têm logins próprios e independentes — cada um busca apenas na sua própria tabela.

Acesso Método Endpoint Descrição
Pública POST /clientes/login Valida credenciais na tabela de Clientes e gera um Token JWT com tipo: "cliente". Falha se o cadastro ainda não tiver email/senha (cliente criado só pelo funcionário).
Pública POST /funcionarios/login Valida credenciais na tabela de Funcionários e gera um Token JWT com tipo: "funcionario".

Exemplo JSON - Login do Cliente

{
  "email": "marcos@email.com",
  "senha": "456"
}

Exemplo JSON - Login do Funcionário

{
  "email": "carlos@stopclean.com",
  "senha": "123"
}

Como usar o Token?

Ao autenticar com sucesso, a API retorna um objeto JSON contendo o token de acesso e o tipo de usuário (cliente ou funcionario).

Adicione o token nas requisições protegidas através do Header HTTP:


Authorization: Bearer [COLE_O_TOKEN_AQUI]

O tipo guardado no token é o que define, em cada rota protegida, se o acesso é liberado só para funcionário, só para o próprio cliente, ou para ambos.

Gestão de Clientes e Funcionários

Acesso Método Endpoint Descrição
PúblicaGET/clientes/verificar-cpf/:cpfVerifica se já existe cadastro com esse CPF, e se ele está completo (com email/senha) ou não.
PúblicaPOST/clientes/cadastroCadastro do próprio cliente. Obrigatórios: cpf, email, senha. Se o CPF já existir (criado antes por um funcionário), completa esse cadastro em vez de duplicar.
Protegida (funcionário)POST/clientes/cadastro-funcionarioCadastro de cliente feito pelo funcionário. Obrigatórios: cpf, telefone — sem email e sem senha.
Protegida (funcionário)POST/funcionariosCadastra um novo funcionário (com criptografia de senha via Bcrypt). Só um funcionário já autenticado pode cadastrar outro.
Protegida (funcionário)GET/clientesLista todos os clientes cadastrados.
Protegida (funcionário)GET/funcionariosLista todos os funcionários do sistema.
ProtegidaGET/clientes/1Busca um cliente por ID. Funcionário acessa qualquer um; cliente só o próprio registro.
ProtegidaPUT/clientes/1Atualiza dados do cliente. Funcionário atualiza qualquer um; cliente só o próprio (e não pode alterar cpf, tokens ou totalLavagens).
Protegida (funcionário)DELETE/clientes/1Remove o registro de cliente permanentemente.
Protegida (funcionário)GET/funcionarios/1Busca um funcionário por ID.
Protegida (funcionário)PUT/funcionarios/1Atualiza dados do funcionário especificado por ID.
Protegida (funcionário)DELETE/funcionarios/1Remove o registro de funcionário permanentemente.

Exemplo JSON (POST /clientes/cadastro)

{
  "nome": "Marcos Oliveira",
  "email": "marcos@email.com",
  "senha": "456",
  "telefone": "(11) 99999-9999",
  "cpf": "987.654.321-11"
}

Exemplo JSON (POST /clientes/cadastro-funcionario)

// Requer no Header: Authorization: Bearer Token (funcionário)
{
  "nome": "Marcos Oliveira",
  "cpf": "987.654.321-11",
  "telefone": "(11) 99999-9999"
}

Exemplo JSON (POST /funcionarios)

// Requer no Header: Authorization: Bearer Token (funcionário)
{
  "nome": "Carlos Souza",
  "email": "carlos@stopclean.com",
  "senha": "123",
  "cargo": "Gerente",
  "cpf": "123.456.789-00"
}

Regras de Negócio

  • As senhas nunca são retornadas nas respostas da API (campos omitidos por segurança).
  • Cliente e funcionário têm controllers e rotas próprios — não passam mais pelo CRUD genérico de tabela.
  • O funcionário cadastra o cliente só com cpf e telefone (sem email/senha). Quando esse cliente quiser criar o próprio acesso, ele completa o cadastro em /clientes/cadastro informando o mesmo CPF, mais email e senha.
  • Não é permitido CPF duplicado: se o cliente já tiver cadastro completo (com email e senha), a API retorna erro e orienta a fazer login.
  • O cadastro de um novo funcionário exige estar autenticado como funcionário — não é mais uma rota pública. O primeiro funcionário do sistema deve ser criado direto no banco (ex.: script de seed do Prisma).

Gestão de Veículos e Serviços

Acesso Método Endpoint Descrição
ProtegidaPOST/tipoVeiculosCadastra categorias de veículos (ex: Carro, Moto).
ProtegidaPOST/veiculosRegistra um veículo. Se logado como cliente, vincula ao próprio cliente automaticamente; se logado como funcionário, deve informar idCliente no corpo.
ProtegidaPOST/servicosCadastra serviços base do lava-jato (ex: Lavagem Completa).
ProtegidaPOST/tipoServicosAssocia o serviço ao tipo de veículo definindo preço e duração.
ProtegidaGET/veiculosLista veículos (se cliente, apenas os seus; se funcionário, todos).

Exemplo JSON (POST /veiculos)

// Requer no Header: Authorization: Bearer Token
{
  "placa": "ABC1234",
  "marca": "Toyota",
  "modelo": "Corolla",
  "cor": "Prata",
  "idTipoVeiculo": 1
}

Exemplo JSON (POST /tipoServicos)

// Requer no Header: Authorization: Bearer Token
{
  "idServico": 1,
  "idTipoVeiculo": 1,
  "preco": 60.00,
  "duracao": "00:45:00"
}

Regras de Relacionamento

  • Se logado como Cliente, a rota /veiculos injeta automaticamente o ID do utilizador autenticado — o cliente não consegue cadastrar veículo para outra pessoa.
  • Se logado como Funcionário, ele informa manualmente o idCliente do dono do veículo.
  • Cliente só consegue ver, atualizar ou remover os próprios veículos (GET/PUT/DELETE /veiculos/:id); tentar acessar o veículo de outro cliente retorna 403.
  • A tabela TipoServico atua como matriz de preços e tempos variados por categoria veicular.

Gestão de Agendamentos e Vínculos

Acesso Método Endpoint Descrição
ProtegidaPOST/agendamentosCria um novo agendamento de lavagem.
ProtegidaGET/agendamentosLista agendamentos. Funcionário vê todos; cliente vê apenas os próprios.
ProtegidaPOST/servicoAgendamentosVincula o serviço específico, o funcionário responsável e o preço aplicado ao agendamento.
ProtegidaPUT/agendamentos/1Atualiza status do agendamento (ex: de AGENDADO para EM_ANDAMENTO).

Exemplo JSON (POST /agendamentos)

// Requer no Header: Authorization: Bearer Token
{
  "idCliente": 1,
  "idVeiculo": 1,
  "data": "2026-07-15T00:00:00.000Z",
  "horario": "1970-01-01T10:00:00.000Z",
  "statusAgendamento": "AGENDADO",
  "valorTotal": 60.00
}

Exemplo JSON (POST /servicoAgendamentos)

// Requer no Header: Authorization: Bearer Token
{
  "idServico": 1,
  "idAgendamento": 1,
  "idFuncionario": 1,
  "precoAplicado": 60.00,
  "obs": "Cliente solicitou secagem extra nas rodas."
}

Fluxo Operacional

O ecossistema do lava-jato conecta o cliente, seu veículo, o serviço contratado através da tabela TipoServico e o funcionário executor via ServicoAgendamento.

O cliente só visualiza, atualiza ou cancela os próprios agendamentos (idCliente igual ao seu ID) — o acesso a agendamento de outro cliente retorna 403.

Controle de Permissões e Segurança no Back-end

Acesso Método Endpoint Descrição
ProtegidaPOST/permissoesCadastra regras de acesso CRUD por tela para os funcionários.
ProtegidaGET/permissoesLista todas as permissões concedidas.
ProtegidaPUT/permissoes/1Atualiza níveis de acesso (visualizar, criar, alterar, excluir).

Exemplo JSON (POST /permissoes)

// Requer no Header: Authorization: Bearer Token
{
  "idFuncionario": 1,
  "nomePermissao": "Controle Total de Agendamentos",
  "tela": "Agendamentos",
  "visualizar": true,
  "criar": true,
  "alterar": true,
  "excluir": true
}

Arquitetura de Segurança

Para evitar vulnerabilidades, o sistema conta com um Middleware de Permissões no back-end:

  • Intercepta requisições POST, PUT e DELETE.
  • Valida automaticamente se o funcionário possui a permissão correspondente para aquela tabela/tela no banco de dados.
  • Gerentes e administradores possuem acesso total nativo, garantindo flexibilidade operacional sem comprometer a segurança.
